  科技树完美命中两种心理：花掉这局赚的金币，永久变强，下一局从更高基线开始。这是所有 Roguelike 游戏最核心的留存钩子——"死亡有意义"。

  ---
  为什么科技树应该先解锁

  1. 复杂度梯度
  - 科技树：花金币 → 点节点 → 得永久属性。三步，无需收集，无需理解稀有度
  - 装备系统：需要理解槽位、稀有度、3件合成、强化消耗、套装效果。认知负担是科技树的5倍

  新手第一局结束，认知带宽最低，应该先给最简单的那个。

  2. 装备系统需要"积累"才有意义
  第一局结束后，玩家手里的装备数量和品质都很薄。如果这时候解锁装备界面，玩家打开一看——三个槽只能装几件白色装备，属性提升极其有限。解锁了但没东西装
  ，体验是失望而不是惊喜。

  而科技树不依赖积累：金币拿来就能点，立刻生效，立刻有反馈。

  3. 行业验证的顺序

  Roguelike 行业标准做法：
  - Hades：第一次死亡 → 解锁"镜子"（永久天赋树）→ 之后才解锁装备/武器系统
  - Dead Cells：第一次通关 → 解锁永久技能树 → 之后解锁武器合成
  - Vampire Survivors：进化/永久升级先，复杂装备后

  都是"永久进度树优先"的顺序。这是行业经过大量数据验证的结论。

  4. 微信小游戏特有的留存压力
  微信小游戏用户流失速度极快，第一局结束如果玩家找不到"变强理由"，当场流失。科技树能把玩家留在游戏里的路径是：

  ▎ 失败 → 打开科技树 → 发现能永久强化生命值 → 花金币升级 → "好，下一局应该能撑更久" → 继续玩

  这条路径装备系统提供不了（因为装备不足）。

  ---
  最终推荐顺序

  ┌────────────────────────┬──────────┬──────────────────────────────────────────────────────┐
  │        触发条件        │ 解锁内容 │                         原因                         │
  ├────────────────────────┼──────────┼──────────────────────────────────────────────────────┤
  │ 第一局结束（无论胜负） │ 科技树   │ 抗失败钩子，简单直接，立刻可用                       │
  ├────────────────────────┼──────────┼──────────────────────────────────────────────────────┤
  │ 通关第二章难度1        │ 装备系统 │ 此时玩家已积累足够装备，认知成熟，能充分体验系统深度 │
  └────────────────────────┴──────────┴──────────────────────────────────────────────────────┘

● 这是个很关键的产品决策，两个选项都有明显陷阱，我给你分析清楚：

  ---
  两个选项的风险

  选项1（预留接口，免费直接复活）的最大风险：

  玩家会形成"免费领取"的肌肉记忆。等流量主开通、广告上线后，玩家感受的是体验倒退——"之前点一下就复活，现在要看广告？"这种落差比从来没有复活功能更容
  易引发差评和流失。微信小游戏的评分机制对这类"先给后收"非常敏感。

  选项2（去掉广告图标，纯净体验）的最大风险：

  广告上线时是一次彻底的体验断层。玩家从"无广告游戏"变成"有广告游戏"，心理落差极大，同样引发负面反馈。

  ---
  推荐方案：保留 UI，标注"公测福利"

  做法：保持所有广告位的 UI 交互不变，但把按钮文案改成明确表示"临时免费"的措辞：

  ┌──────────┬──────────────────────────┬─────────────────┐
  │  广告位  │      现在的按钮文案      │   广告上线后    │
  ├──────────┼──────────────────────────┼─────────────────┤
  │ 复活按钮 │ 免费复活（公测福利）     │ 看视频·复活     │
  ├──────────┼──────────────────────────┼─────────────────┤
  │ 双倍奖励 │ 免费双倍领取（公测福利） │ 看视频·双倍领取 │
  ├──────────┼──────────────────────────┼─────────────────┤
  │ 技能重置 │ 免费再抽一次（公测福利） │ 看视频再抽一次  │
  ├──────────┼──────────────────────────┼─────────────────┤
  │ 体力补充 │ 公测期间免费             │ 看视频·获取体力 │
  └──────────┴──────────────────────────┴─────────────────┘

  为什么这样最合理：

  1. 预期管理：玩家从第一天就知道这是"临时福利"，广告上线时不存在"被偷偷改了"的感知
  2. 习惯培养：交互流程完全一致，玩家已经养成"点复活按钮"的行为习惯，广告上线只是多了一步看视频
  3. 数据价值：能真实观察玩家点击复活的频率、哪个广告位被使用得最多，这是真实的转化意愿数据
  4. 零浪费：UI 开发成本全部保留，广告上线只需要改文案 + 接入 SDK 回调

  上线广告时只需要两步：
  1. 改按钮文案（"公测福利" → 广告描述）
  2. 在按钮回调里接入 wx.createRewardedVideoAd() 替换掉直接发奖励的逻辑

  ---
  结论：你找到的「场景分析→新建场景」是正确的。

  微信小游戏（小程序）的分析体系和小程序不同：

  ┌────────────────┬──────────────────────┬─────────────────────────────────────┐
  │                │      微信小程序      │             微信小游戏              │
  ├────────────────┼──────────────────────┼─────────────────────────────────────┤
  │ 自定义事件 API │ wx.reportAnalytics() │ wx.reportScene() / wx.reportEvent() │
  ├────────────────┼──────────────────────┼─────────────────────────────────────┤
  │ 后台位置       │ 数据分析→自定义分析  │ 统计→基础数据→场景分析→新建场景     │
  └────────────────┴──────────────────────┴─────────────────────────────────────┘

  所以你在后台找不到"自定义分析"是正常的——小游戏根本没有这个模块。小游戏的自定义事件追踪就是用「场景分析」来做的。

  使用方式：
  1. 在后台「场景分析→新建场景」创建一个场景（例如"第一局战斗开始"），系统给你一个 sceneId
  2. 在代码里调用 wx.reportScene({ sceneId: 'xxxxx' }) 上报

  关键限制：场景分析是只记录"到达/触发"次数的漏斗型统计，每个场景只能记录"发生了几次"，不支持携带自定义参数（比如记录死在第几波、选了哪个技能）。

  这意味着我方案里部分带参数的事件（如 battle_end 携带 waves_cleared、build_type 等）无法通过场景分析实现。

  对文档的影响：
  - 所有漏斗类、里程碑类事件（到达/完成某步骤）→ 用场景分析 ✅
  - 所有带参数的数据分析事件（战斗摘要、技能分布等）→ 暂时只能靠现有 BattleStatistics 本地 CSV，或后续接友盟 SDK

  我的建议：文档分两层设计：
  - 一期（场景分析，现在就能做）：漏斗节点 ~15 个场景
  - 二期（等接友盟或自建后端）：带参数的深度事件
