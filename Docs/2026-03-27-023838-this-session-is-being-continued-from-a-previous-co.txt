● Unity 灰色脚本的原因

  这是 Unity 的**序列化引用失联（Serialized Reference Orphan）**问题，具体机制：

  1. TurretHealth 组件挂载在场景对象上，Unity 通过 MonoScript 的 GUID + fileID
  将组件实例与脚本文件绑定
  2. 我通过外部工具（非 Unity 内置编辑器）多步编辑脚本文件时，Unity
  的文件监听器可能在某次中间态（如 using 语句已写入但方法体还没完成）触发重编译
  3. 编译中间态失败 → Unity 把场景中的 TurretHealth 组件标记为「脚本丢失」→
  这个脏状态被缓存进 Library/
  4. 后续即使脚本本身已经正确，缓存未清除，组件依然显示灰色且无报错（因为序列化
  层的错误不走 Console）

  为什么重启解决，预制体解决：
  - 重启 Unity 清空了 Library 缓存，重新建立绑定
  - 转成 Prefab
  后，序列化路径从「场景内嵌对象」变成「资产文件引用」，重建了干净的 GUID 绑定

  后续建议：重要 GameObject 都做成
  Prefab，一方面规避这个缓存问题，另一方面也符合项目规范。

  关于第二阶段数据模型：顶级策划用什么？

  TTK 是其中一个工具，但不是全部。对于塔防 Roguelite 
  类型，业界通用的完整框架如下：

  一、核心框架：双曲线对齐模型（Power Curve vs Threat Curve）

  玩家战力曲线  DPS(wave)     ▲
                              │      /理想DPS
                              │    /
                              │  /  实际DPS(各流派)
                              │/
  ────────────────────────────┼──────────► wave
                              1  3  5  7  9

  敌人威胁曲线  HP+Speed(wave)▲
                              │         /
                              │       /
                              │     /
                              │   /
  ────────────────────────────┼──────────► wave

  设计目标：玩家DPS曲线的最低值（最差构建路线）需高于敌人HP曲线要求的最低清场DPS
  。

  二、具体用到的模型层

  层1：TTK锚点模型（波次通关可行性）

  Required_DPS(W) = Enemy_Total_HP(W) / Target_Clear_Time(W)
  Actual_DPS(W)   = Panel_DPS(W) × Efficiency_Factor

  这是最基础的检验：每波的 Panel_DPS 能否在目标时间内消灭当波怪物总血量。

  层2：EHP生存预算模型（玩家不死性）

  Total_Damage_Capacity = Hull_HP + Shield_HP = 3000
  Cumulative_Damage(W1..W9) = Σ(HP损耗)
  Safety_Margin = 3000 - Cumulative_Damage

  从你的4局数据看：
  - 暴击流最危险：累计损耗约1790（Hull-790 + Shield-1000）
  - 冰冻流最安全：累计损耗约470
  - 这个安全裕量差距是3.8倍，说明流派间生存体验差异很大

  层3：DPS成长效率模型（Roguelite核弹点）

  DPS_Growth_Rate(build) = ΔPanel_DPS / Δlevel

  这是 Roguelite 与普通塔防的核心差异——需要建立每种流派的成长效率曲线，确保：
  - 快速成型的流派（暴击流第5级就成型）不能太强
  - 慢热流派（分裂流需要堆 Wide/Chain）不能太弱

  层4：Deal Contract 经济模型（契约性价比）

  Deal 无人机是这个游戏的特殊机制（用HP/护盾换DPS增益），需要建立：

  Contract_Efficiency = ΔDPS_gain / HP_cost
  Break_Even_Wave = HP_cost / (ΔDPS × Kill_per_wave_benefit)

  即：这笔交易在第几波回本？
