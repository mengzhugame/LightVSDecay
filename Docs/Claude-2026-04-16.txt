好的，来逐条思辨：

  ---
  ① 护盾受伤（OnPlayerShieldDamaged）→ 建议取消

  取消理由：游戏核心玩法是激光塔防，绝大多数时间玩家护盾都在持续被小怪碰撞。一大波怪涌上来，0.5s 节流也救不了——每半秒震一次，一
  整波下来手机不停颤，跟手柄漏电没区别。震动的价值在于"传递信息"，而护盾受伤是常态，不需要专门信息提示。结论：删除。

  ---
  ② 本体血量受伤（OnPlayerHealthDamaged）→ 建议保留，但配合重节流

  保留理由：护盾破碎后才能打到本体，这是玩家最危险的状态。此时震动="你快死了，快修盾！"是高价值信息，而不是噪音。只要设 1.5s
  节流，就算多怪同时打，感知上是"中震一次 + 停顿"，不会连续颤动。
  取消理由：如果你觉得护盾破碎的震动（见③）已经足够提醒，本体受伤可以删；重复信息没必要。
  建议：保留，节流 1.5s；如果测试后感觉多余再删。

  ---
  ③ 护盾破碎 → 强烈建议保留

  保留理由：这是战斗中最关键的"状态转折点"——从安全变为危险。一次性重度震动（400ms）是最精准的信息载体，告诉玩家"你的防线垮了"。
  不频繁（一局顶多破几次盾），是震动系统里性价比最高的一个点。

  ---
  ④ BOSS 死亡 → 同意取消，改做子弹时间

  取消理由：BOSS 死亡本身视觉表现已经很强（爆炸、特效、胜利
  UI），震动属于锦上添花且可能干扰观感。你说的子弹时间方向更对——慢动作 + 画面特效 +
  音效就够了，震动在这个节点显得粗糙。结论：删除，另做子弹时间。

  ---
  ⑤ BOSS Press（角力/碾压）→ 建议取消

  取消理由：Press 是持续 5-10
  秒的角力状态，期间玩家注意力集中在角力进度条上。持续震动=玩家手一直在颤，不仅不爽还会影响操作精度。而且 Press
  已有视觉（进度条、力场特效）传达信息，无需震动补充。结论：删除。

  ---
  ⑥ BOSS 入场吼声 → 建议新增，而且做差异化

  保留理由：BOSS 从屏幕边缘移动到战场中心完毕，然后发出吼叫——这一刻是"危险即将开始"的预告节点，一次重度震动（600ms）完美传达"庞
  然大物出现了"。配合已有的 CameraShake，手感会非常有冲击力，且只触发一次，不会令人反感。结论：在 SpawnRoutine
  吼叫那行代码旁加震动 + 镜头抖动。

  ---
  ⑦ 大招激活 → 同意取消

  取消理由：你的分析完全正确——大招已有视觉特效，玩家可能提前憋着大招等时机，这段时间手机如果一直有"激活震动"的期待感反而造成焦
  虑。结论：删除。

两个 BUG 均已修复并推送。下面是具体分析：

  ---
  Bug 1：遮罩不显示（编辑器 / 真机通用）

  根因：Unity 对 inactive 的 GameObject 不调用 Awake()，会把它推迟到首次 SetActive(true) 时同步执行。Show() 里调用
  gameObject.SetActive(true) 触发了 Awake()，而 Awake() 末尾有 if (!debugMode)

  修复：引入 _showRequested 标志位。Show() 在调用 SetActive(true) 前将其置 true，让 Awake() 跳过自隐藏，SetActive
  返回后立即复位。

  ---
  Bug 2：真机纯黑 + 点击无反应

  根因：分两层——

  1. 纯黑遮罩：Shader 未加入 Always Included Shaders，Shader.Find("UI/HoleMask") 返回 null，_holeMaskMaterial 为 null →
  纯黑色覆盖（你已通过添加 Shader 解决）。
  2. 点击无穿透：UpdateShaderHole() 原来的第一行是 if (_holeMaskMaterial == null || _target == null) return;，material
  为 null 时直接返回，导致 _holeScreenHalfSize 永远是 Vector2.zero。IsPointInHole() 检测到这个零值会直接返回
  false（不在洞内），IsRaycastLocationValid 对所有触摸点返回 true（全部拦截），按钮完全无法触发。

  修复：将孔洞屏幕坐标计算与 Shader 赋值解耦——只要 _target != null 就先算出
  _holeScreenCenter/_holeScreenHalfSize/cornerRadius，最后再判断 _holeMaskMaterial == null 才提前 return，不写 Shader
  属性。这样即使 Shader 加载失败，点击穿透逻辑依然正常工作。

好问题，三种方式各有用途，不是互斥的。让我解释清楚：

  ---
  ShaderVariantCollection 是什么

  Android 打包时，Unity 把 Shader 源码编译成 GPU 字节码。但 Shader 有很多"变体"（比如开关了某个 keyword 的版本），Unity
  默认在首次渲染时才编译对应变体 → 这就是首次用到某种怪物/特效时的那一帧卡顿。

  ---
  三种方式的区别

  方式: Always Included Shaders
  用途: 强制把整个 Shader 所有变体打进包
  你需要吗: 只适合小型/特殊 Shader（如你的 UI/HoleMask）。全部 Shader 这么做会让包体暴增
  ────────────────────────────────────────
  方式: ShaderVariantCollection + Warmup()
  用途: 精确记录游戏实际用到的变体，打包时只包含这些，运行时一次性预热
  你需要吗: 这是正确方式
  ────────────────────────────────────────
  方式: 手动代码 Warmup()
  用途: 调用已有的 .shadervariants 文件做预热
  你需要吗: 配合上面那个一起用

  ---
  推荐做法（两步）

  第一步：录制变体文件

  在 Unity 编辑器里：

  1. Edit → Project Settings → Graphics，找到 "Shader Variant Collection" 区域
  2. 点击 "Save to asset" 或者用菜单 Window → Analysis → Shader Variant Collection 打开面板
  3. 在编辑器 Play 模式下，把游戏从头玩一遍（每个章节至少走一遍，让所有材质都渲染一次）
  4. Unity 会自动追踪用到的所有 Shader 变体
  5. 停止 Play 后，在 Graphics 页面点 "Save to asset"，保存为 Assets/ShaderVariants/GameShaderVariants.shadervariants

  第二步：运行时预热

  在 GameManager.OnSingletonAwake() 里加载并预热（文件路径放进 Inspector）：

  [Header("Shader 预热")]
  [SerializeField] private ShaderVariantCollection shaderVariantCollection;

  然后在 OnSingletonAwake() 里：

  if (shaderVariantCollection != null)
      shaderVariantCollection.WarmUp();

  放在 Application.targetFrameRate = 60 之后即可。WarmUp() 会同步编译所有已录制的变体，通常在 Loading

  ┌─────────────────────┬────────────────────────────────────────────────────────────────────────┐

  ├─────────────────────┼────────────────────────────────────────────────────────────────────────┤

  │ 太快消失            │ Start Lifetime 和 Duration 拉长到 1~2 秒                               │
